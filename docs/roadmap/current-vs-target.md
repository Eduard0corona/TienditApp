# Estado actual vs arquitectura objetivo

| Área | Estado actual comprobado | Objetivo aprobado | Estado |
|---|---|---|---|
| Despliegue | Monolito modular API+SPA, DB compartida | Mantener; evaluar servicios solo por escalamiento/aislamiento/ownership/cadencia | Decisión |
| Capas | Cuatro proyectos Clean Architecture con pruebas de dependencias en CI (Fase 4F); las reglas que vivían en Infrastructure (respuestas automáticas, clientes temporales, estados de entrega del webhook) están en Application (Fase 7C) e Infrastructure solo adapta Meta, correo y almacenamiento | Dependencias estrictas y casos de uso siempre en Application | Alcanzado |
| Tenant | Filtro global en toda entidad con `TenantId`, también configuración, WhatsApp, partidas e historial de estado (Fase 8C), middleware por membresía, interceptor que rechaza `TenantId` ajeno o modificado, hubs con membresía, workers y webhook en el alcance de su negocio (Fase 6), cada `IgnoreQueryFilters()` revisado en una lista (Fase 4) y una suite HTTP con dos negocios contra SQL Server (Fase 8C); el override `X-Tenant-Id` solo se audita en el log y la suite aún no incluye hubs ni webhooks | Cobertura total, tenant inmutable, políticas explícitas y suite cross-tenant | En progreso |
| Autorización | Cada caso de uso declara su regla (permiso, membresía, módulo) y Application la evalúa; controllers sin roles y hubs por membresía (Fase 5B) | Policies/resource authorization consistentes en backend | En progreso |
| Eventos | Outbox durable con worker, reintentos y dead-letter para auditoría y avisos de pedidos (Fase 2); recordatorios, campañas y avisos de citas por la cola de mensajería (Fases 2 y 6); SignalR tras el commit (Fase 4G) con Azure SignalR opcional (Fase 5E) | Outbox durable + consumidores idempotentes antes de procesos críticos | En progreso |
| Fiscal | IVA por negocio y por producto, desglose persistido por línea, claves SAT y vista previa CFDI 4.0 (Fases 1 y 3); sin timbrado | Tax Calculation Engine México, desglose persistido, preparación CFDI | En progreso |
| Ajustes financieros | Pagos/caja sin ledger de ajustes | Créditos/débitos trazables, CxC, saldo a favor, Wallet y conciliación | Objetivo no implementado |
| Inventario | Libro mayor único para insumos y productos (Fase 5A), folios por contador (Fase 4F), tokens de concurrencia en existencias, costo y recepción; la recepción de compra aún sin llave de idempotencia | Concurrencia robusta, transferencias atómicas y reconciliación | En progreso |
| Clientes | Registro por negocio con notas y direcciones, ficha con pedidos y chat, y bajas de mensajería por negocio (Fases 2 y 4D); sin lealtad ([ADR 0009](../adr/0009-loyalty-per-business.md)) | Registro por negocio con consentimiento, historial y lealtad | Lealtad fuera de alcance |
| API | `/api/v1`, `ProblemDetails` uniforme con código (Fase 4F), OpenAPI versionado con los nombres de cada enum y cliente generado, enums incluidos (Fase 7B); algunos listados pequeños sin paginar | `ProblemDetails` uniforme, tokens propagados, paginación completa | En progreso |
| Frontend | Lazy routes, TanStack Query sobre el cliente generado, pruebas con Vitest (Fase 5C), lint de accesibilidad (Fase 6F) e Inventario dividido por pestaña (Fase 7D); Vender y Pedidos aún superan 1,000 líneas | Componentes más pequeños y pruebas automatizadas | En progreso |
| Seguridad | CORS allowlist, secretos fuera del repo (pendiente rotar), uploads validados por firma; comprobantes y fotos de servicio privados con descarga autorizada (Fase 8A); refresh tokens solo como hash, con rotación, detección de reuso y sesiones revocables que invalidan el access token (Fase 8B); 2FA y rate limit | Uploads con descarga autorizada, secretos rotados y gestionados, tokens revocables, pruebas security | Bloqueante preproducción (rotar secretos) |
| Pruebas | xUnit de Domain, Application, Infrastructure y WebApi; pruebas contra SQL Server 2022 (Fase 4F) y Azurite (Fase 8A) en CI, del cliente (Fase 5C) y de la API completa entre dos negocios (Fase 8C) | Pirámide con SQL Server, API, tenant y frontend | En progreso |
| Operación | `apply.sql` por migración, probado en CI con `sqlcmd` y aplicado antes del merge; la prueba de humo exige `/health/schema`; slot de staging con swap y aprobación listo para activar (Fase 7A); CI y deploy con gates de build/test/lint/migraciones/audit; OpenTelemetry y health checks (Fase 2) | Migraciones productivas controladas y observabilidad | En progreso |

No hay aprobación para implementar estos objetivos dentro de tareas ajenas. Cada uno requiere issue/ADR/alcance y validación propios.
